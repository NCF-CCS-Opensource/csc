# NestJS API with Clean Architecture and single-action controllers

Business logic moves out of `apps/web` into a new `apps/api` NestJS service built in four inward-pointing layers — domain (entities and repository interfaces), application (use cases), infrastructure (Drizzle adapters and mappers), presentation (controllers, DTOs, presenters). Each HTTP action is a **single-action controller** mapped 1:1 onto exactly one use case, routed RPC-style as `POST /v1/api/<resource>/<action>`.

A future reader should know this was **not** forced by a technical problem. The trigger was Supabase's free tier pausing inactive projects, which a `DATABASE_URL` change alone would have fixed (ADR-0018); at the time of this decision `apps/web/lib/db.ts` was the entire database coupling and no Supabase SDK existed anywhere in the codebase. The rewrite is a deliberate investment in structure, made while the system was pre-launch with no live data and therefore nothing to migrate and nothing to break.

Modules under `apps/api/src/modules/`: `student`, `enrollment-roster`, `semester`, `event`, `attendance`, `scan`, `penalty`, `payment`, `program`, `ledger` (ADR-0021), `report` (ADR-0020).

## Considered Options

- **Move hosting only, keep Next.js server actions** — rejected, but it was the cheaper and strictly sufficient answer to the stated problem, and it is recorded here so nobody later assumes the rewrite was the only way out of Supabase.
- **REST routing (`POST /v1/api/events`, `PATCH /v1/api/events/:id`)** — rejected: this domain is command-heavy (approve, reject, correct, record-payment, materialize, promote, sign clearance) and forcing those onto REST verbs invents ceremony while breaking the 1:1 controller↔use-case mapping that is the point of single-action controllers.
- **No `v1` prefix** — rejected: the booth app ships as an installed Android binary that cannot be redeployed in lockstep with the API, so a version prefix is the only thing standing between a breaking change and every Officer's phone failing mid-semester.
- **Rewrite the domain logic from scratch rather than porting it** — rejected: the Ledger's no-show materialization and Scan Approval's idempotency are the two genuinely subtle parts of this domain (ADR-0008, ADR-0009), and re-deriving them from prose invites reintroducing bugs already paid for. Thin CRUD is generated by `pnpm generate:resource`; the hard parts are ported by hand with their tests.

## Consequences

- `apps/web/lib/architecture.integration.test.ts` (~38 tests against a disposable Postgres) is the acceptance gate for the port. It is transport-agnostic — it describes use cases, not Next.js — and it must be green before any module is considered migrated.
- Everything served by the dyno is subject to Heroku's **H12 30-second hard request timeout**. This is why report rendering stays on Vercel (ADR-0020).
- During the strangler migration, Event logic genuinely exists twice — in Next.js serving mobile, and in NestJS serving web — until mobile repoints (ADR-0006, as amended).
- `packages/db` becomes an `apps/api` dependency only (ADR-0019).
